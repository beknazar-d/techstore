# Phone Market — инструкция для агентов

Интернет-витрина магазина электроники и гаджетов: смартфоны, ноутбуки, наушники, часы,
техника Dyson, фены, аксессуары. У сайта две части:

- **Клиентская** — каталог, карточка товара, заявка на заказ.
- **Админка** (`/admin`) — товары, категории, склад, заказы.

## Как работают агенты

**Оркестратор — Fable** (`claude-fable-5-2`). Он берёт на себя всё сложное:
архитектуру, модель данных, бизнес-логику (склад, заказы, RLS, безопасность),
разбор непонятных багов. Сам код он пишет только тогда, когда объяснить задачу
дольше, чем сделать.

Fable раздаёт задачи остальным агентам:
1. Делит задачу на шаги, каждый шаг затрагивает 1–3 файла.
2. Объёмную работу (вёрстку, компоненты, CSS-модули, формы, тексты, рутинный код)
   отдаёт бесплатным моделям через **neurogate**:
   - `neurogate delegate --file <задача.md>` — агент правит файлы в проекте;
   - `neurogate ask --file <вопрос.md>` — ответ без правки файлов.
   Задачу всегда пишет в файл (на Windows перенос строки обрезает аргумент), файл
   кладёт во временную папку, а не в проект. Команды идут 1–10 минут, поэтому
   таймаут нужен большой. Не отвечает — `neurogate doctor`.
3. Исполнитель не видит разговора, поэтому задача пишется полностью: какие файлы,
   что сделать, какие правила из этого файла соблюсти, как проверить результат,
   что считается готовым.
4. После каждого шага Fable смотрит изменения (`git diff`), запускает `npm run build`
   и `npm run lint`. Если результат плохой, отправляет исправление с конкретикой:
   что сломано, где и как должно быть.

Только Fable или сам пользователь делает то, что трудно отменить: миграции на боевой
базе Supabase, деплой, секреты, удаление данных.

**Если ты исполнитель** (получил задачу через neurogate): выполни только её,
никому дальше не передавай, архитектуру не меняй, лишних файлов не трогай.
Если задача противоречит этому файлу, остановись и опиши проблему в отчёте.

## Журнал работы, коммиты, проверка

- **Журнал — `docs/PROGRESS.md`.** После каждого законченного раздела ТЗ допиши туда:
  что сделано, ключевые файлы, принятые решения, что осталось и известные проблемы.
  Пиши коротко, это память между сессиями. **Новую сессию начинай с чтения
  `docs/PROGRESS.md`**, а не с полного анализа кода.
- **Коммиты** — после каждого законченного раздела, на английском, коротко и чётко
  в стиле Conventional Commits: `feat: add product order modal`,
  `fix: prevent ordering more than stock`. Одна строка, тело только при необходимости.
- **Docker** (установлен глобально) — после подключения Supabase и Cloudflare
  проверяем через него: локальный Supabase (`supabase start`), прогон миграций,
  Edge Functions и сборки. До этого он не нужен.

## Главные правила бизнеса

- **Онлайн-оплаты нет.** Нигде нет способов оплаты, полей карты, рассрочки.
- Клиент отправляет **заявку на конкретный товар**, оплата — **при получении, на месте**.
- **Корзины нет.** Одна заявка = один товар + количество.
- Клиенту не нужна регистрация. Вход только для администратора.
- **Склад списывается автоматически.** Было 100 шт., оформили заявку на 1 — стало 99.
  При отмене заказа товар возвращается на склад. Нельзя заказать больше, чем есть.
- О каждой новой заявке администратор получает сообщение в **Telegram-бот**.
- Кроме новой техники продаём **б/у устройства** (в основном смартфоны). У каждого
  указаны состояние, здоровье аккумулятора, дефекты и комплект.
- Есть **трейд-ин**: клиент оставляет заявку на своё старое устройство (с фото),
  магазин оценивает его и звонит. Клиент сдаёт старое устройство и доплачивает
  разницу за новое — тоже на месте, без онлайн-оплаты.
- Сайт должен оставаться **простым**. Не добавляй функции (корзина, избранное,
  сравнение, отзывы, оплата, личный кабинет) без прямой просьбы пользователя.

## Текущий этап: сайт на Supabase

- Данные — в Supabase. Вся работа с данными идёт **только через слой `src/api/`**
  (supabase-js, RPC). Компоненты не ходят в Supabase напрямую.
- Склад, заказы, trade-in, статистика — функции базы (RPC); RLS на всех таблицах.
- Вход в админку — Supabase Auth + таблица `admins` (строку добавляет Fable или пользователь).
- Telegram: Edge Functions `telegram-webhook` (сообщения клиентов → «Чаты») и `telegram-admin`
  (подключение, ответ менеджера, тест группы). Токен админ вставляет в «Настройках»,
  он хранится зашифрованным в Supabase Vault (RPC `bot_token_*`, только service_role).
  Уведомлений в группу о заказах пока нет — следующий шаг.
- ИИ — на выбор Claude, ChatGPT или Gemini (отдельно для ассистента и для бота). Ключи провайдеров
  и ElevenLabs админ вставляет в «Настройках» → Vault (RPC `ai_secret_*(p_provider)`), провайдеры, модели,
  голос и указания — таблица `ai_settings`. Общий слой вызова моделей — `supabase/functions/_shared/llm.ts`
  (нейтральный формат сообщений). Edge Function `ai-admin`: подключение ключей и шаг ИИ-ассистента.
  Голос бота (`_shared/voice.ts`): на голосовое клиент получает голос + текст; распознавание и озвучка —
  ElevenLabs (голос/аватар по Voice ID, лучше для кыргызского) или OpenAI.
  Инструменты ассистента (`supabase/functions/ai-admin/tools.ts`) выполняет браузер через `src/api/ai.ts`
  теми же функциями `src/api`, что и формы; удаления у ассистента нет. Кружок — `src/admin/components/AiAssistant`.
  ИИ-ответы бота — `supabase/functions/_shared/botAi.ts` (поиск товаров, торг не ниже `min_price`,
  заявка через `create_order`, передача менеджеру, отвечает на языке клиента — ru/ky); при сбое ИИ
  чат уходит менеджеру.
- Языки — русский и кыргызский (`src/i18n/`, без библиотек): `msg()`/`useT()`, тексты по областям
  в `src/i18n/ru/*.ts` и `src/i18n/ky/*.ts`. Новые тексты интерфейса — только через них, в обоих языках.
- Фото — **временно** сжатый data URL в базе (миграция `trade_in_photos_interim`). Дальше — R2.
- `src/data/seed.ts` → `supabase/seed.sql` только для локальной базы (`supabase db reset`).
- `.env.production` — публичные URL и anon-ключ для боевой сборки; секретов там нет.

## Сжатие фото

Перед загрузкой каждое фото **сжимается в браузере** (`src/utils/compressImage.ts`,
через canvas, без библиотек): длинная сторона не больше 1600px, формат WebP с качеством
около 0.8, а если браузер WebP не умеет — JPEG. Исходник в хранилище не попадает.

## Архитектура

```
Браузер (React SPA)  ──►  Supabase (Postgres + Auth + Edge Functions)
   │                           │
   │                           └──► Telegram Bot API (уведомление о заказе)
   │
   └── фото товаров ◄── Cloudflare R2 (публичный домен)
Хостинг SPA — Cloudflare Worker «techstore» (статика из dist)
```

Правило хранения: **тяжёлые файлы (фото) — в Cloudflare R2, все данные — в Supabase**
(товары, заказы, trade-in, переписка Telegram-бота, настройки бота).

- **Frontend:** React 19 + Vite + TypeScript, `react-router-dom`, `@supabase/supabase-js`.
  Одно приложение; админка — роуты `/admin/*`, загружаются лениво (`React.lazy`).
- **Backend:** Supabase. Бизнес-логика — в Postgres-функциях (RPC) и Edge Functions.
  Отдельного сервера нет.
- **Фото:** Cloudflare R2. Загрузка из админки через подписанную ссылку, которую выдаёт
  Edge Function `upload-url`. В базе храним только публичный URL.
- **Хостинг:** Cloudflare Worker `techstore` со статикой (`wrangler.jsonc`: `dist`,
  `not_found_handling: single-page-application`). Адрес: `techstore.sadyrbekov981-ae2.workers.dev`.
  **Автодеплой — Workers Builds:** каждый push в `main` → `npm run build` → `npx wrangler deploy`.
  Push в `main` = выкладка на боевой сайт. `VITE_*` переменные задаются в панели Cloudflare
  (Worker → Settings → Build → Variables), а не в репозитории.
- **Supabase:** проект `zicvjjxrkpwcwtiepqdq` привязан к репозиторию (GitHub-интеграция).
  `supabase/config.toml` содержит боевые настройки входа — не возвращай туда localhost-значения.
- **Секреты** (ключи R2, service role Supabase) — только в секретах Edge Functions.
  Токен Telegram-бота — в Supabase Vault: админ вводит его на сайте, Edge Function
  `telegram-admin` проверяет и сохраняет, обратно во фронтенд он не возвращается.
  Ключ Anthropic — так же, через `ai-admin` в Vault.
  Во фронтенде — только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.

## Модель данных (Supabase)

**categories** — категории товаров
- `id`, `name`, `slug`, `sort_order`, `is_active`
- `spec_fields jsonb` — шаблон характеристик для этой категории, например
  `[{ "key": "screen", "label": "Экран", "unit": "дюйм", "type": "number" }, ...]`.
  Для «Смартфонов» — экран, память, камера, аккумулятор; для «Фенов» — мощность,
  режимы, насадки; для «Ноутбуков» — процессор, ОЗУ, SSD и т.д.
  Админ сам задаёт поля при создании категории.

**products** — товары
- `id`, `category_id`, `name`, `slug`, `brand`, `description`, `price` (целое, в рублях)
- `condition` (`new` | `used`); для б/у — `used_info jsonb`: состояние
  (`excellent` | `good` | `fair` — Отличное / Хорошее / Удовлетворительное),
  здоровье аккумулятора %, гарантия (мес.), дефекты, комплект
- `stock int` (остаток на складе, `>= 0`), `is_active`
- `images text[]` (URL фото в R2, первое — главное)
- `specs jsonb` — значения характеристик по ключам из `spec_fields` категории
  (`{ "screen": 6.1, "memory": "256 ГБ" }`)
- `created_at`, `updated_at`

**orders** — заявки
- `id`, `number` (короткий номер для клиента), `status`:
  `new` → `confirmed` → `completed` (можно сразу `new` → `completed`), либо `cancelled`
- товар: `product_id`, `product_name`, `price` (копия на момент заказа), `quantity`
- клиент: `customer_name`, `customer_phone`
- получение: `delivery_type` (`pickup` | `delivery`), `address`,
  `location_lat`, `location_lng` (если клиент поделился геолокацией),
  `desired_date`, `desired_time` (куда и во сколько приехать)
- `comment`, `admin_note`, `created_at`

**trade_ins** — заявки на трейд-ин
- `id`, `number`, `status`: `new` → `evaluated` → `accepted` | `rejected` → `completed`
- клиент: `customer_name`, `customer_phone`
- устройство клиента: тип, бренд, модель, память, состояние, аккумулятор %, дефекты,
  комплект, `photos text[]` (сжатые, до 5 шт.)
- `desired_product_id` + снимок названия и цены — на что хочет обменять (необязательно)
- `admin_estimate` (сколько предлагаем, ₽), `admin_note`, `comment`, `created_at`
- изменения пишутся в историю, как у заказов

**bot_settings** — одна строка: настройки Telegram-бота (имя бота, ID группы менеджеров,
какие уведомления слать, приветствие, инструкция для ИИ, разрешён ли торг, может ли бот
оформлять заявки, передавать ли разговор менеджеру). Токен бота сюда НЕ пишется — он
в Supabase Vault; в таблице лишь последние 4 символа для показа.

**bot_chats** — переписка с клиентом в Telegram: `telegram_chat_id`, имя, username, телефон,
`mode` (`bot` | `manager` | `closed` — кто отвечает), `handoff_reason`, `order_id`,
`unread_count`, последнее сообщение.

**bot_messages** — сообщения: `chat_id`, `sender` (`customer` | `bot` | `manager`), `text`,
`created_at`. Ответ менеджера переводит чат в `manager`, и бот в нём замолкает.

**admins** — `user_id` из Supabase Auth. Админ = пользователь, который есть в этой таблице.

### Логика и безопасность

- RLS включён на всех таблицах.
- Аноним: читает только активные `categories` и `products`. В `orders` напрямую
  не пишет и не читает.
- Заявку создаёт Edge Function `create-order`: проверяет поля → вызывает RPC
  `create_order` → отправляет сообщение в Telegram → возвращает номер заказа.
- RPC `create_order` (security definer) в одной транзакции: блокирует строку товара
  (`for update`), проверяет `stock >= quantity`, уменьшает `stock`, создаёт заказ.
  Нехватка товара → понятная ошибка «Недостаточно товара на складе».
- RPC `cancel_order` возвращает количество на склад. Повторная отмена ничего не делает.
- Админ (проверка через `admins`) имеет полный доступ ко всем таблицам.
- Схема меняется только миграциями в `supabase/migrations/`.

## Клиентская часть

| Путь | Страница |
| --- | --- |
| `/` | Главная: баннер, категории, популярные товары |
| `/catalog`, `/catalog/:categorySlug` | Каталог с фильтром по категории |
| `/product/:slug` | Карточка: фото, цена, остаток («В наличии» / «Нет в наличии»), характеристики из `specs`, кнопка «Заказать» |
| `/trade-in` | Как работает трейд-ин (3 шага) + форма заявки с фото |

В каталоге есть фильтр «Новые / Б/У», на главной — блок «Б/У смартфоны». На карточке
б/у товара — бейдж состояния, аккумулятор, дефекты, комплект. На карточке нового
смартфона есть кнопка «Обменять старый (trade-in)», которая открывает форму
с уже выбранным товаром.

«Заказать» открывает модалку с формой: имя*, телефон*, количество, самовывоз/доставка,
адрес (для доставки), кнопка «Отправить мою геолокацию», желаемые дата и время,
комментарий. Под кнопкой — «Оплата при получении». После отправки — экран
«Заявка №… принята, мы свяжемся с вами».

## Telegram-бот (CRM)

Бот делается под этот сайт и работает как CRM-помощник. **Это следующий этап.**
Сейчас его не делаем, но архитектура должна это позволять.
- **Уведомления в группу** менеджеров (`TELEGRAM_GROUP_ID`) о каждом новом событии
  в базе: новая заявка (все данные клиента и товара, ссылка на карту и на заказ
  в админке), смена статуса, отмена, товар закончился или осталось мало.
- **Разговоры с клиентами:** отвечает на вопросы о товарах и наличии, принимает
  заявку прямо в чате, **торгуется** в пределах, которые задал админ.
  Например, у товара есть `min_price`, и ниже этой цены бот не уступает.
  Сложные случаи передаёт живому менеджеру.
- Действия менеджера кнопками в группе: «Подтвердить», «Отменить», «Выполнен».
- Реализация на следующем этапе: Supabase Edge Function как webhook бота +
  Database Webhooks на таблицы. Для разговоров — LLM, данные о товарах она берёт
  из базы, а не выдумывает.

Поэтому в данных уже сейчас: у заказа есть `source` (`site` | `telegram`),
у товара есть необязательный `min_price` (видит только админ), а каждое изменение
заказа пишется в историю (`order_events`), чтобы бот мог на неё реагировать.

## Планы: приложения для администратора

Позже админку выпустим ещё в двух видах. Оба **только для администратора**,
клиентская часть в них не входит:
- **Десктоп** — приложение на Electron (Windows).
- **Android** — APK, сборка через Capacitor.

Оба приложения будут оборачивать тот же React-код из `src/admin/`, а не копию.
Поэтому уже сейчас при работе над админкой:
- `src/admin/` не импортирует клиентские страницы. Общие компоненты лежат в `src/components/`.
- Админка ходит только в Supabase, без запросов к относительным путям сайта.
- Не завязывайся на браузерные мелочи без запасного варианта: геолокация, `window.open`
  и скачивание файлов в приложениях работают иначе.
- Вёрстка админки должна быть удобной на телефоне (APK), а не только на десктопе.

Делать эти приложения сейчас не нужно, пока пользователь не попросит.

  Без Tailwind, styled-components, inline-стилей и UI-библиотек.
- Цвета, радиусы, тени и отступы — только переменные из `src/styles/tokens.css`.
  Hex-цвета в модулях не пишем. Новый токен добавляем в `tokens.css`.
- Классы — camelCase (`styles.productCard`). Сначала мобильная вёрстка, потом
  `@media (min-width: 768px)`.
- Иконки — Material Symbols Outlined: `<span className="material-symbols-outlined">call</span>`.
- Шрифт — Inter.

## Дизайн

Макеты: `design/design/*/` (`code.html` + `screen.png`), дизайн-система —
`design/design/a7store_retail_system/DESIGN.md`. Берём **стиль**, а не всё содержимое:
белый фон, тонкие рамки `1px var(--color-border)` вместо теней, карточки с радиусом 16px,
фото 1:1 на `--color-surface-warm`, синий цвет только для кнопок действий,
зелёный бейдж «В наличии», кнопки высотой 48px, модалки с радиусом 16–24px.
Админка — в том же стиле, но плотнее (таблицы и списки).

Не переносим: корзину, способы оплаты, рассрочку, Москву и iPhone из текстов.
Папка `design/` — только для справки, её не редактируем.
